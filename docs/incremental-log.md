## The brief (from the owner, word for word)

Use workflows to make Tide & Toll look and feel like one designed game overnight, without me. Build until 07:00 Amsterdam time (06:00 UTC on 27 November), then show me a review page. I will answer yes or no per item and say continue.

My input from playing the Windows build (commit b797857)
- The game is fun to play. Do not change how it plays unless a step below says so.
- The interface, the models and the popups feel off. The interface layout is the worst: it feels chaotic.
- I did not answer the review page. Use your own judgement and its "What still looks wrong" list.

Goal
Keep the play as it is. Make the interface calm and ordered, make popups behave as one system, and make the town beautiful to look at.

Order of work (do not stop between steps)
1. The interface layout. This is the main job of the night: give it the first rounds and at least a third of the time.
   - Start with an audit: a screenshot of every state of the screen in both ages (early, middle and late game, shop open, modes on, pages open, book view, pause, settings), at 1920 x 1080 and 1280 x 720. Have reviewers mark everything that competes for attention, overlaps, jumps about or has no clear place.
   - Then design before building: one layout with fixed zones, each with one job (for example: coin and level in one place, things to buy in one place, the current goal in one place, messages in one place), a clear order of importance, one grid, one set of margins and sizes. Write it as a one-page layout sheet with a mock-up, have two reviewers criticise it, and only then build it.
   - Rules for the result: the middle of the map stays free; nothing moves when something else appears; at most a handful of things ask for attention at once; finished and locked items fold away; the same thing is always in the same place in both ages.
   - One set of card, button, label and number styles used everywhere, with clear hover, pressed, disabled and "you can afford this now" states, and tooltips that say what a purchase does and what it is worth.
   - Nothing overlaps or is cut off at 1280 x 720 and 1920 x 1080, at interface sizes 80, 100 and 150 percent, in both ages. Test it.
2. Popups as one system.
   - List every popup, banner, card, hint, note, coin number and page the game can show, and when.
   - Build one message system: each kind has one fixed place, a priority and a length of stay; messages queue instead of stacking; only one large one shows at a time; none covers the thing it is about; small things (a delivery, a purchase) never raise a large popup.
   - All of them arrive and leave with the same eased motion as the book, never in one frame. Extend the game-motion test to cover them.
   - A first minute that teaches itself: three or four short hints that appear when needed and never again.
3. Models and other assets: spend real quality time here, at least a quarter of the night and never less than two full rounds.
   - Start with an audit: a contact sheet of every model, texture, icon and sound, each at the normal view and close up. Rank them worst first against the Living Map style, and write a one-page style sheet (palette, outline weight, proportions, level of detail) that every asset is checked against.
   - Improve the old ones, worst first. Known weak ones: the extended cottage (thin, a dark box from above, sizes hard to tell apart), villagers and what they carry, trees, the mill, the market stall, boats, the crossings, the charter and seal stones, the book's paper, leather and table. Rework each until it holds up close and at the normal view; don't just recolour.
   - Add new ones: at least three variants of the cottage so a street does not repeat, a proper icon for every upgrade and achievement, more props and small touches, animals, and ambient life (chimney smoke, birds, shimmer on the river, washing on a line).
   - Everything made in code as before, each with a ledger row. Show before and after for every reworked asset.
4. Feel: small rewards on every action (a coin pop at the delivery, dust on a new trail, a ripple at the landing, a bell swing), each with its sound. Keep them light: the per-frame cost test must still pass.
5. Finish the book's motion: speed carried over when an animation is interrupted, the two bookmark cards that pop in, the leaf's paper matching the book's paper, and a turning leaf that looks like a leaf, not a wipe.
6. If there is time left: play the second age by real input from start to borough seal and fix what that finds (river villagers walking home to first-age cottages, the ford mattering on only half of the towns); then a title page when the game starts (the closed book with Continue, New town, Settings, Quit).

Keep
- How the game plays, the engine set-up, the tests, the one-command check, the Windows build on GitHub, the Living Map art style, the music, the book and its animations, and the save format (old saves must still load, or be migrated with a test).

Roles: you (Fable 5.2) lead, plan, review and decide; don't write game code. Haiku 5.5: quick lookups, doc reading, licence checks, bug hunts. Sonnet 5.5: research, design criticism, code review, play-testing. Opus 5.5: building and fixing.

Rules
- Don't ask me anything. Where a decision is mine, take your recommended option and log it under "Decisions made for you". If something needs my approval (a new network host, a login, spending), skip it and log it under "Needs you".
- Update the design doc first (https://claude.ai/artifact/Ld2BuxHtt8Ht8LpRbVxeJT): put the layout sheet, the message system and the style sheet in the UX and Art tabs, and tonight's plan in the Build Plan tab.
- Judge looks from pictures, not from code: after every round take screenshots, have them read by a reviewer who did not build them, and fix what they find before calling the round finished.
- Commit and push to Marten-Mrfc/Tide-Toll on the claude/prototype-1 branch after every round. No pull requests, no pushes to main. Start work-in-progress commit messages with "Snapshot" so GitHub only builds an exe for finished rounds, and wait for a build to finish before pushing again.
- Make the loop survive a container restart: keep exactly one scheduled check pending, and resume interrupted rounds from the log (docs/incremental-log.md).
- Never send a message to an agent inside a running workflow; put what it needs in a file its brief reads. Give agents clock deadlines, not durations.
- €0 budget. No asset without a ledger row. Nothing with a non-commercial or unclear licence.
- Never weaken a test to make it pass. Report failures plainly. Tests that only fit the old layout may be replaced by the equal test for the new one; say which and why.
- After the layout round and at the end, play a whole first age with real input and confirm the pacing did not get worse (charter near minute 33, decisions per minute per ten minutes).

Stopping
- Start no new round after 05:00 UTC, so everything is reviewed, pushed and built by 06:00 UTC. Run the whole check on a clean copy of the final commit. Cancel the scheduled check when you stop.
- Then publish a review page as an Artifact and post the same list here. At least 40 numbered pictures at 1920 x 1080 from the final build, each with one line saying what it shows and one yes-or-no question for me:
  - before and after, side by side, for every screen of the interface and for every reworked asset;
  - every kind of popup in its place;
  - the layout at 1280 x 720 and at interface sizes 80 and 150 percent;
  - the new assets, close up and in the town;
  - anything that still looks wrong.
- End with: the link to the newest Windows build, what got better and what did not in your honest view, "Decisions made for you", "Needs you", and the list of new sounds to listen to.
